# What was changed with respect to the original `srasel.py`

**Base of the engine (updated 2026-11-09).** `src/srasel/engine.py` is built from the **English version** of SRASel 2.0 received on
2026-11-09 (`legacy/srasel_2.0_english_received.py`, 6633 lines), with the edits below. The Spanish file the work started from
(`legacy/srasel_2.0_original.py`, 6448 lines) is kept untouched. Both hashes are in `legacy/SHA256`.

*How the two versions were compared.* Parsing both files to syntax trees with every string and docstring masked, only these
differences in logic remain: (a) `_short_paths` + `_HOME_PATH` shorten home-based paths shown in the report/log; (b) `load_ref` adds the
keys `gs` / `ge` to the mature-peptide entries of the report data; (c) the report provenance key `generado` is now `generated`;
(d) `--seed` of `run` has a help text; (e) the `get_cmap` fallback (edit 1) and the covariation start day (edit 6) were already in the received file.
Nothing else differs in logic. **Limits of that comparison:** it cannot see the *value* of a string, and strings that act as data were
translated (e.g. the gene fallback `non-coding`, the transfer statuses `discarded` / `transferred`, the neutral class `drift`, output names
`report.html`, `SUMMARY.md`, `tsv_time_sets`, log markers `Step N`, `[WARNING]`). It was therefore also *measured*: the English file
reproduces the golden exactly on both synthetic cases, the only exceptions being the translated text report `REFERENCE_REPORT.txt`
(the golden copy is now the English text) and the pandas ≥ 3 `[NaN]` display issue that edit 2 fixes. **Not exercised by the golden:**
`transfer-annotation` statuses, the `non-coding` fallback, `--truth` / `drift`, mature-peptide data (`gs`/`ge`).

Everything below was re-applied on the English file and re-verified (golden, resume, robustness, web, browser).
Nothing that computes a number, a filter, a model or an annotation was modified by the package.

## Report host contract (edit 11)

The report is one self-contained file. A host page (local web, online page) that shows it in `<iframe sandbox="allow-scripts">` and draws its own sub-tab bar uses:

| | |
|---|---|
| Tab ids | `summary` · `variants` · `traj` · `genes` · `quality` · `about` (labels Summary, Variants, Trajectories, Genes, Quality, About); `sim` (Simulation) and `val` (Validation) exist only when the report was built with `--truth` / `--neutral` / `--notes` |
| Address | `report.html#tab=<id>`. A click on a tab rewrites the address (`history.replaceState`, no history entry); a change of the hash of the iframe `src` fires `hashchange` and switches the tab; unknown ids are ignored. Other keys the page writes: `p` (series), `a` and `d` (p and \|Δf\| thresholds, only when not SRASel's own), `g` (gene), `dir`, `v` (open variant). Old links with `t=<id>` still work |
| Embed | `#embed=1` hides the report's own title, light/dark button and tab bar; the selection bar (thresholds, gene, direction, series) and the tab content stay. The flag is kept when the page rewrites the address. `#embed=0` switches it off. When it is not set nothing changes |
| Theme | `#theme=light` or `#theme=dark` forces the theme (without it the page follows `prefers-color-scheme`) |
| `srcdoc` hosts | A `srcdoc` document cannot carry a hash, so the host sends `iframe.contentWindow.postMessage({type: "srasel-report", tab: "variants", embed: true, theme: "dark"}, "*")` (every key optional; messages of another `type` or from another window are ignored). The report answers its parent with `{type: "srasel-report", event: "ready" \| "tab", tab, tabs: [[id, label], …], embed}` (only ids and labels), so the host can build its bar from `tabs` and follow the tab |
| Downloads | The figure buttons (SVG, PNG) and the table button (TSV) create a file in the page. **A sandboxed iframe without `allow-downloads` blocks them** (checked in Chrome: `sandbox="allow-scripts"` gives no download, adding `allow-downloads` gives it, and it does not add an origin or any other right). The host decides whether to add it. **Both hosts do since 2026-11-20 (phase 3):** the local page and the online page use `sandbox="allow-scripts allow-downloads"` (the local report response carries the same value in its CSP `sandbox`); a figure button was checked in Chrome to deliver a file inside the local iframe |

Tested in `tests/unit/test_report_redesign.py` (address, embed, message and iframe cases).

## Open scientific decisions (NOT changed; need the authors' approval) – from [STATS_AND_REPORT_AUDIT.md](../validation/A_scientific/earlier/STATS_AND_REPORT_AUDIT.md)
* **p resolution vs number of dates (B2/B3):** the exact p never falls below 1/n_dates!. With 3 dates nothing can be labelled; with 4 dates (min p ≈ 0.042) the label depends on Monte Carlo noise and mirror alleles of one site can get different labels (golden: phiX P1 1236 C/G, LCMV P2 7662). Exact enumeration would change results.
  **Decision (owner, 2026-11-04): keep the method as is; document it.** README and both UIs state: 3 dates = no tag possible, 4 = borderline, 5 or more recommended. Mirror alleles (same site, complementary alleles getting different labels) also stay as they are.
  **Replicates of the same day (H1):** pooling by summing depths is kept unchanged; the owner will consult a colleague and report back.
* **Covariation annotation (A2):** `--covar-min-days` and `--covar-min-range` are accepted but have no effect (also in 1.x). A1 (Δday always 0) was fixed, see edit 6.
* **Help/report texts that do not match the code (A3/A4):** the ≥100-read filter is on the allele count k, not total depth; `selected_ranked` is sorted by signed score; the report hard-codes 0.03, 2000 and 1/2000 in places; JS uses p ≤ α, Python p < 0.05.
